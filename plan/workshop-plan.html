MCP Apps with React: Build Interactive UI That Runs Inside Claude and ChatGPT

Attendees start from a working MCP server and a React view with marked gaps. They fill the gaps, with an agent if they have one. Most of the time goes to what each piece of the official SDK does and why. Everything runs locally and offline, with no accounts.

Builds: Expensify, the INR expense tracker from the masterclass Stack: @modelcontextprotocol/ext-apps 2.x · MCP TypeScript SDK v2 · React 19 · Vite · tenet-ui tokens Audience: intermediate React developers, with no MCP experience needed
What the CFP promises, used as a guide rather than a contract

What the plan keeps from the CFP, and what it changes

Three changes from the submitted outline: MCP itself gets 20 minutes, deployment gets its own short section, and A2UI moves to a stretch goal for whenever time is left over.

  • The server comes pre-built. Attendees touch only the few lines that turn a tool into an app.
  • The React view has marked gaps (🔨 3.3 markers), each one short, with a hint and the full solution next to it.
  • Understand first, then fill. Each SDK export is explained before anyone writes it.
  • JSON-RPC is shown in a protocol log, not drawn on slides.
  • A real local MCP Apps host. No paid account, no API key, no tunnel.
  • Works offline after install, checked a week ahead by an install script.
  • Node 20+ and a Chromium browser. The coding agent is optional for every step.
  • Same build fits Claude and ChatGPT: map the host's tokens onto a small design system.
  • One deliberate CSP debugging exercise, plus the sandbox and permissions.
  • Deploy it (new): the same server on Cloudflare Workers' free plan, then a short demo of the same build in Claude, ChatGPT, VS Code Copilot, Gemini and more. A2UI only if time is left over.
Decisions

How I'd meet those promises

A workshop host, forked from the SDK's

The ext-apps basic-host example (built on AppBridge) gets vendored into host/ and extended into the host every attendee runs on localhost:8080. It shows a conversation, the view, and a live protocol log covering both connections: host to server and host to view.

No local host shows both connections at once, and the CFP leans on reading that traffic in sections 1, 4 and 5. With no model running, attendees call tools by hand, and anything the view says to "the model" shows up in the log and the conversation.

Host theme presets

A switcher in the host's toolbar sends host-context-changed with a Claude-like or ChatGPT-like set of style variables, each in light and dark.

That keeps the promise that the same build fits Claude and ChatGPT, offline, without opening either. The real apps appear only in the final demo.

MCP Inspector for section 1

It's installed as a dev dependency, so it works offline. The server exposes all three primitives: tools (expenses), a resource (expenses://categories) and a prompt (monthly_review).

"Tools, resources and prompts on the wire" is what Inspector's history pane already shows. Section 1 needs nothing built for it.

tenet-ui as the "small design system"

The view styles itself with tenet-ui 0.4.0's tokens. A single host-bridge.css points those tokens at the host's variables, with tenet's values as fallbacks.

It's your own design system, it's already on npm, and its semantic tokens (--fgColor-default, --borderRadius-medium) map one to one onto the host's.

Problem and solution folders, plus a playground

Every step is a pair of folders: 01.problem.connect and 01.solution.connect. You work in a single playground/ folder. npm run go 3.1 loads a step, npm run diff compares your work with the solution, and npm run solution copies the answer in.

The folder idea is borrowed from Epic Web's workshops, because it works: no git skills, no tags, and the answer is always one folder away. The rest is our own, designed for a room where agents do most of the typing.

Designed for agents first, still easy for humans

Every command is non-interactive. It takes its arguments as flags, never prompts, exits non-zero on failure, and prints plain text, or JSON with --json. Markers in the code are a small set of emoji with a fixed meaning, listed in AGENTS.md, so agents read them as reliably as people do. npm run status answers "where am I, and what's left?" for a person and an agent alike.

Agents get stuck on prompts and on output meant only for eyes. Emoji are easy for people to scan, and once AGENTS.md defines them, agents follow them too. One format serves both, so an attendee can switch between typing and delegating halfway through a step.

AGENTS.md is the rulebook. CLAUDE.md and GEMINI.md point at it.

AGENTS.md is read natively by Cursor, Copilot and Codex. CLAUDE.md and GEMINI.md are each one line, @AGENTS.md. The rules say this is a step-by-step workshop: run npm run status first, edit only playground/, do only the current step's 🔨 markers, never read *.solution.* unless asked, run npm test, and then answer the step's "Explain it back" questions in chat.

Without these rules, an agent would happily finish the whole app in one go, or copy the solution, and the learning would be lost. With them, the agent fills one gap and then teaches the attendee what it did.

1 · MCP in practice

0:00 · 23 min (20 of it MCP) · follow along

A real grounding in MCP before any UI. About 8 minutes on why MCP exists and how its architecture works, then a live walk through the running Expensify server in MCP Inspector. Attendees run npm run inspect and click along.

Attendees do

  • Read the expenses://categories resource and get the monthly_review prompt
  • Open each message in the history pane

You should see: initialize, tools/list, tools/call, resources/read and prompts/get, each with a request and a response.

Explain
  • Why MCP: the N×M integration problem, and one protocol between any agent and any tool
  • Host, client and server, and who controls each primitive: the model calls tools, the app attaches resources, the user picks prompts
  • The lifecycle: initialize and capability negotiation, then requests and notifications
  • JSON-RPC by example: id, method, params, result and notifications, read off the log
  • A tool result: content for the model, structuredContent plus outputSchema for code. That's the hook for the rest of the workshop.
  • Transports in one line: stdio and Streamable HTTP. We use HTTP on localhost.

How the exercises work

One step, start to finish

Each step is a complete, runnable copy of the app. The problem copy has 🔨 markers where the code should go. The solution copy has the code. Shared pieces (the workshop host, the data store, the presentational components) live outside the steps, so problem-to-solution diffs show only the MCP code that the step teaches.

// playground/ui/mcp-app.tsx, after `npm run go 3.3`
  const { app, error } = useApp({
    appInfo: { name: 'Expensify', version: '1.0.0' },
    capabilities: {},
    onAppCreated: (created) => {
      // ✅ 3.2  tool input seeds the filters
      created.addEventListener('toolinput', ({ arguments: args }) => setRange(seedFrom(args)));

      // 🔨 3.3  Listen for 'toolresult'. The host sends it once, when the tool finishes.
      //         Read result.structuredContent, check it with isSummary(), then setSummary().
      // 💡  created.addEventListener('toolresult', (result) => { ... })
      // 🧠  content is what the model reads. structuredContent is what your UI reads,
      //     shaped by the tool's outputSchema. The view never parses the model's text.
      // 📡  In the log: ui/notifications/tool-result, host to view.
      // 📖  https://apps.extensions.modelcontextprotocol.io/api/ (App events)
    }
  });
Eight step markers

🔨 Build: what to write, with its step number (🔨 3.3). 💡 Hint: the shape of the answer. 🧠 Why: the reason it works this way. 📡 Traffic: which messages to find in the protocol log. 📖 Docs: a spec or SDK link. 🧪 Test: what npm test checks. 🔥 Bonus: extra credit for fast finishers. ✅ Done: work from earlier steps. Every one is a single character, so grep -rn "🔨" playground reliably finds every open task.

The step README

The goal and a screenshot, the task, the 🧠 explanation the "Understand" slides follow, which messages to find in the protocol log, and what breaks without it. It ends with 2 or 3 "Explain it back" questions.

The scripts

npm run status shows the current step, the open markers with their file and line, and the test result. go 3.3 loads a step and backs up the playground. diff, solution and npm test. All non-interactive, and all accept --json.

Shortcuts for agents

/step 3.3 as a Claude Code command (.claude/commands/) and as a Copilot prompt file (.github/prompts/). In any other agent, "do step 3.3" does the same thing, because AGENTS.md says how.

  1. Deploy target: Cloudflare Workers?Recommended: yes. It's free, needs no card, it's what the masterclass server already uses, and the fetch-shaped handler moves over with a tiny worker.ts. One caveat: the CFP says "no accounts", so the deploy step is optional for attendees, and the pre-event email can suggest making a free Cloudflare account.
  2. Is a forked workshop host fine, instead of the stock basic-host?Recommended: yes. The CFP's "read the protocol traffic" and "fits Claude and ChatGPT" promises both need it. The host is used, not built, by attendees.
  3. Use tenet-ui as the "small design system"?Recommended: yes, the token mapping is about 12 lines. An alternative is a tiny 10-token system written just for the workshop.
